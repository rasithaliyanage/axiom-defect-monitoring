1. What stays the same, what the domain changes The architecture from the beginner guide carries over unchanged. Frontend and backend remain the system and deployment view; presentation, domain, AI and data remain the logical view; UI Runtime, Domain Runtime and AI Runtime remain the AI-native runtime view; and harness plus Claude Code plus tests plus evals plus feedback remain the engineering layer. The rule that AI recommends while the Domain Runtime decides is unchanged, and the Generative UI principle that a model selects from an approved component vocabulary rather than emitting executable code is unchanged. Three things the domain does not change: the runtime boundaries, the deterministic-versus- probabilistic split, and the position of Claude Code in engineering time rather than in the product runtime. What the domain does change is deployment topology and the shape of the users. Four consequences follow, and they are the only reasons this tree differs from the one in the beginner guide. The same three runtimes are deployed twice. An inspection system has a factory edge tier that must keep working without the enterprise, so UI, Domain and AI Runtime code is composed into two deployment targets rather than one. This is a deployment concern, not a second architecture, which is why edge/ and enterprise/ hold composition only and never business logic. There is no customer. The UI Runtime serves operators, inspectors and quality managers, so Generative UI shifts from landing-page composition to role-aware review and inspection surfaces, and the approved component catalogue changes accordingly. The Domain Runtime gains line equipment as a consumer. PLC, MES and quality-system adapters exist, and no inference may reach line equipment without passing the decision path. The AI Runtime is vision-first rather than language-first, which makes the model lifecycle a substantial engineering area in its own right. 9. Structural rules this layout protects Each of these is a reason a directory exists where it does. If any of them is violated, the structure has stopped helping. ml/preprocessing/ is imported by ai/vision/ at serving time. Preprocessing must exist once, not once in training and again in inference — duplicated preprocessing is the classic cause of training and serving skew, and it surfaces as unexplained recall loss in production rather than as a failing test. contracts/ sits above the three runtimes so that an edge decision and its later central re-analysis remain comparable, and so no runtime owns the wire format. policies/ is separate from code because thresholds and taxonomy are Quality-owned. The repository copy is the seed and default; the runtime source of truth is the policy service behind the admin surface, so a threshold change is an audited business action rather than a deployment. backend/adapters/ is the only place permitted to talk to line equipment, which keeps protocol detail out of the decision path and makes every integration testable against simulators/ . simulators/ exists because a coding agent with no way to exercise degraded capture, a latency breach or a disconnected enterprise will write happy-path code with confidence. evals/runner/ is executable and wired into ci/ . A rubric that is not run decays within weeks. edge/ and enterprise/ hold composition only. Inspection logic accumulating there means the service boundaries were drawn in the wrong place. No directory layout enforces anything. Three invariants in particular need tests that prove they cannot be bypassed, not folders that suggest it: No path from inference to line equipment that skips the decision path Evidence persisted before any action is taken on a board A HOLD is never resolved by timeout — an expiring HOLD turns a capacity problem into a quality escape 10. Open decisions before committing In priority order, because the first two change the shape of the tree and the rest only change its contents. 1. Deployment granularity. backend/services/ is a logical decomposition, not nine deployable services. For a first build, one deployable with enforced internal module boundaries is almost certainly right, extracting later where throughput or release cadence demands it. Decide this explicitly before anyone reads the tree as a microservice mandate. 2. Repository strategy. Edge devices and the enterprise platform will not ship on the same cadence. A single repository works initially, but release tagging per component is needed early, and a later split of the edge tier should be anticipated rather than discovered. 3. Technology stack. The beginner guide names React, TypeScript, Python, FastAPI and PostgreSQL. Those are illustrative here. The BRD defers infrastructure and deployment, and the vision workload plus the edge hardware target should drive the choice. Record it in docs/adr/ . 4. Policy runtime source of truth. Confirm that policies/ is the seed and the policy service is authoritative at runtime, and define how a policy version is pinned into a decision record. 5. Edge decision autonomy. Whether layers 5 and 6 are approved to run at the edge for offline continuity determines how much of ai/ and backend/ ships to the line, and it depends on the unresolved answer to what happens when the enterprise is unreachable. 12.
